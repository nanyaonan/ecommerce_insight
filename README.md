# 电商经营数据洞察 API（ecommerce_insight）

> 一个把「业务数据」变成「人能看懂的经营结论」的后端服务项目。
> 传统聚合接口负责算准数，大模型负责把数字说成人话——**大模型全程不接触数据库**。

---

## 一、它解决什么问题

商店后台堆着订单数据，但数据本身不能帮人做决定。这个项目把数据加工成三层服务：

| 层 | 回答什么问题 | 由谁出力 |
|---|---|---|
| 统计层 | 卖了多少、哪天涨了、哪个品类最好 | SQL 聚合查询 |
| 解读层 | 这些数字意味着什么、该怎么做 | DeepSeek 大模型 |
| 问答层 | 关于历史经营情况的追问 | 周报知识库 + 大模型（RAG） |

核心设计取舍：**能用 SQL 精确算出来的，绝不交给模型猜**；大模型只处理「算不出来」的那部分——判断、归因、表达。

## 三、架构

```
                    ┌──────────────────────────┐
   HTTP 请求  ───▶   │      FastAPI 接口层       │
                    └────────────┬─────────────┘
                                 │
        ┌────────────────────────┼────────────────────────┐
        │                        │                        │
        ▼                        ▼                        ▼
┌───────────────┐      ┌────────────────┐      ┌──────────────────┐
│  统计/写库     │      │   AI 解读       │      │   RAG 问答        │
│ 接口 ①②③④⑥   │      │   接口 ⑤        │      │   接口 ⑦          │
└───────┬───────┘      └────────┬───────┘      └────────┬─────────┘
        │                       │                       │
        │              —只把算好的数字传出去—              │
        │                       │              ┌────────┴────────┐
        │                       │              │ ① 程度类→SQL排序 │
        │                       │              │ ② 其余→检索周报  │
        │                       │              └────────┬────────┘
        ▼                       ▼                       ▼
┌─────────────────────────────────────┐      ┌──────────────────┐
│         PostgreSQL（唯一数据源）      │      │  DeepSeek API    │
│  product_type / orders / reports    │      │  外部大模型服务    │
└─────────────────────────────────────┘      └──────────────────┘
```

**两条铁律**（这是本项目最重要的设计）：

1. **LLM 不直连数据库。** 应用层查数、算数，把结果拼进提示词；模型只能看到数字，看不到表。安全边界清晰，也不会出现「模型自己编一个数」。
2. **求和、排序、最高最低这类确定性计算由 SQL 完成。** 大模型的长处是语言，不是算术；把比较大小交给它，等于让它在可能不含正确答案的候选集里猜。

## 四、数据设计

| 表 | 内容 | 说明 |
|---|---|---|
| `product_type` | 8 个品类 | 女装、数码、美妆、食品、家居、运动、母婴、图书 |
| `orders` | 10000 条订单 | 近九个月，含金额、时间、状态、品类、用户 |
| `reports` | 57 篇周报 | 按 ISO 周聚合生成，供问答层作为知识库使用 |

造数口径（有意贴近真实业务）：

- 品类分布走二八法则，权重 `[0.30, 0.20, 0.18, 0.10, 0.08, 0.06, 0.05, 0.03]`
- 订单金额服从对数正态分布（μ=4.2，σ=0.6），均值约 80 元——少量高价单拉长尾部，比均匀分布真实
- 周末订单密度为工作日的 1.3 倍（拒绝采样实现），造数后用 `extract(dow from order_time)` 验证过，周末占比约 33.6%
- 订单状态按 已完成 88% / 待发货 7% / 已取消 5%

**全项目 GMV 口径统一：只统计「已完成」订单。** 五个接口的数字互相印证，任何一个出现口径漂移都会被其他接口打脸。

## 五、接口清单

启动后访问 `http://127.0.0.1:8000/docs` 可直接交互测试。

| # | 方法 | 路径 | 参数 | 说明 |
|---|---|---|---|---|
| ① | GET | `/api/categories` | — | 全部品类及各品类订单量 |
| ② | GET | `/api/gmv` | `start`、`end`（可选） | 大盘 GMV、订单数、客单价 |
| ③ | GET | `/api/trend` | `start`、`end`（可选） | 逐日 GMV 与订单趋势（画折线图用） |
| ④ | GET | `/api/topn` | `start`、`end`、`n`（默认 8） | GMV TopN 品类排行榜 |
| ⑤ | GET | `/api/insight` | `start`、`end`（可选） | **AI 经营解读**：模型用三句话讲大盘、亮点、建议 |
| ⑥ | POST | `/api/orders` | 请求体 `prd_id`、`amount`、`status` | 下单写库，返回新订单 id |
| ⑦ | POST | `/api/rag/ask` | 请求体 `question`、`top_k` | **周报问答**：基于 57 篇周报回答并附出处 |

示例：

```bash
# 大盘
curl "http://127.0.0.1:8000/api/gmv?start=2026-09-01&end=2026-09-30"

# AI 解读
curl "http://127.0.0.1:8000/api/insight?start=2026-09-01&end=2026-09-30"

# 周报问答
curl -X POST "http://127.0.0.1:8000/api/rag/ask" \
  -H "Content-Type: application/json" \
  -d '{"question": "哪一周的GMV最高", "top_k": 3}'
```

## 六、AI 能力的两处关键实现

### 6.1 接口⑤：数字 → 人话

流程：查库 → 把数字拼进提示词 → 调 DeepSeek → 返回解读文字。

提示词做了输出约束（限三句话、不用 markdown），否则模型会输出一篇小作文，前端没法用。外部调用一律带 `timeout`，并先判 `status_code` 再取结果——**网络抖动或余额不足时返回降级文案，而不是 500**。

### 6.2 接口⑦：周报问答（RAG）

标准三段式：**检索 → 增强 → 生成**。

```
用户提问
  ├─ 命中「最高/最低/最多」等程度词 → SQL 排序直接查出唯一答案（精确）
  └─ 其他问题 → LLM 抽关键词 → 周报库 LIKE 检索 → 按命中数取 top_k 篇
                                 → 拼进提示词 → 模型只依据材料作答
```

两个设计点值得说明：

- **答案必须带 `sources`**：RAG 的价值在于可溯源，答案来自哪几篇材料要能当场翻出来。
- **提示词里写死「不得编造」**：材料里没有的信息，要求模型明确回答「材料中没有相关信息」。这条约束是 RAG 和「直接问大模型」的分界线。

**为什么程度类走 SQL**：57 篇周报正文全都包含「GMV」字样，关键词检索会把它们全部命中、得分相同，取出的 top_k 篇与 GMV 高低毫无关系。若把「哪周最高」丢给模型，它会在一份可能不含真正第一名的材料里自信作答——**不报错、语法通顺、数字也真实，但结论是错的**。所以这类问题交给数据库排序，秒回且必然正确。

## 七、快速启动

**前置**：本机已安装并启动 PostgreSQL 16。

```bash
# 1. 建库（只需一次）
createdb ecommerce_insight

# 2. 创建虚拟环境并安装依赖
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 3. 配置环境变量（.env.example 只有键名和占位值，不含真实密钥）
cp .env.example .env
#   编辑 .env：填入本机的数据库串与 DeepSeek 密钥

# 4. 建表 + 造数（10000 条订单 + 57 篇周报，约几秒）
python scripts/gen_data.py

# 5. 启动服务
uvicorn app.main:app --reload

# 6. 打开交互文档
open http://127.0.0.1:8000/docs
```

> 键名以 `.env.example` 为唯一来源，新增配置时先改它，README 不再重复列出。
> `.env` 已在 `.gitignore` 中，真实密钥不会进版本库；`load_dotenv()` 默认只加载 `.env`，不会误读 `.env.example`。

## 八、项目结构

```
ecommerce_insight/
├── app/
│   ├── main.py          # 全部路由 + 业务逻辑
│   └── models.py        # ORM 模型（Base）与接口数据模型（BaseModel）
├── scripts/
│   └── gen_data.py      # 建表 + 造订单 + 生成周报
├── requirements.txt
├── .env                 # 本地配置，不入库
└── .gitignore
```

**为什么分两套模型**：`models.py` 里同时有 SQLAlchemy 的 `Base`（数据库表）和 Pydantic 的 `BaseModel`（接口入参）。二者刻意分开——订单主键、下单时间由服务端生成，不给客户端开口子，这层隔离就是入参的安全边界。

## 九、已知边界（有意为之，非疏漏）

| 项 | 现状 | 生产环境做法 |
|---|---|---|
| 鉴权 | 未做，服务默认仅本机访问 | 引入登录态与 token，服务端解析 user_id |
| `user_id` | 下单接口暂写死为 1 | 从登录态解析，不由客户端传 |
| 服务暴露范围 | 启动不绑 `0.0.0.0`，仅本机访问 | 对外暴露前必须补鉴权 + 只读数据库账号 |
| 检索方式 | 关键词 `LIKE` 匹配 | 知识库达百万级时改用向量检索（embedding） |
| 关键词路由 | 精确匹配，不兼容拼写错误 | 用 LLM 做意图分类替代规则匹配 |
| 中文分词 | 未引入分词库 | 规模上去后引入 jieba 等分词器 |

以上取舍的共同原则：**知道正解是什么、知道当前简版的边界在哪，并把它写下来。**
